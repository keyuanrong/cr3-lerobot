# 项目开发工作流

本流程适用于项目自研的真机、数据、训练、Pi0 远程推理和 MuJoCo 改动。LeRobot 上游改动除遵循本流程外，还应尽量保持与上游接口兼容。

## 1. 明确目标

开始前写清：目标、输入、输出、约束和验收标准。用户需求已明确时不重复追问，也不自行扩大到 UI、数据库、重构或新框架。

示例：

```text
目标：让 Pi0 训练时固定提高总目标抓取片段的出现比例。
输入：四个已转换的本地 LeRobot 数据集。
输出：训练过程每 1000 个样本为 40/25/25/10。
约束：单 GPU；不改变单数据集训练行为。
验收：采样器测试准确计数，训练 CLI 可识别混合配置。
```

## 2. 读取上下文

先确认实现位置、调用者、下游、数据流、已有能力和测试。仓库有 `.codegraph/` 时优先使用 CodeGraph；再用 `rg`、文件读取和最小复现补充。高风险代码必须读到实际发送动作或实际写入数据的边界，不能只根据文件名判断。

## 3. 制定计划

实施前说明：要修改的文件、每处修改目的、明确不修改的文件和验证方式。小改动可短，但不能跳过影响分析。涉及真机、动作语义、坐标/单位、数据格式或 checkpoint 时，应先给出回退或 dry-run 方案。

## 4. 最小修改

按“配置 → 现有接口 → adapter/glue code → 新模块”的顺序处理。不要复制已有转换、归一化、采样或 action 逻辑；避免在 `scripts/`、`src/lerobot/` 和 `sim/` 各做一套同功能实现。

代码改动遵循测试优先：先写能复现新需求或缺陷的测试，确认失败，再实现最小修复并确认通过。

## 5. Quality Gate

按风险选择至少一个对应层级的验证。

| 改动类别 | 最低验证 | 额外要求 |
| --- | --- | --- |
| 文档、命令说明 | Markdown 路径/命令静态检查 | 不宣称未执行过的命令可用 |
| 纯 Python 工具、筛选、转换 | 目标单测 + 小样本 dry-run | 检查输入输出数量、帧范围、任务文本 |
| Dataset / Processor / 归一化 | 单测 + 打开数据集读取样本 | 检查 feature 名、shape、dtype、夹爪语义 |
| 训练/采样器 | 单测 + CLI 参数检查 + 小步训练 | 记录数据版本、配置、seed、loss；不能只靠 loss 下结论 |
| MuJoCo 控制/映射 | 单测或数值断言 + 回放/短 rollout | 检查关节符号、单位、actuator ctrlrange、碰撞/稳定性 |
| 远程推理 | 服务端加载 + client dry-run + 延迟/动作日志 | 检查图像键、action chunk、队列、夹爪去抖 |
| 真机接口/控制 | 连接与观测检查、限速/限幅 dry-run | 先仿真或回放；只在明确确认后 `--execute` |

## 6. 检查修改范围

完成后确认：

- 改动文件数量与计划一致；没有误删或无关格式化。
- 没有重复代码、临时 debug 输出、硬编码机器路径或密钥。
- 没有无必要的抽象层，且未替换成熟上游能力。
- 当前目录有 Git 时执行 `git status`、`git diff --check`、审阅 `git diff`。
- 当前目录无 Git 时，列出修改文件并以针对性测试、编译/语法检查和命令输出替代 diff 审查。

## 7. 记录结果

不同类型的工作记录不同证据：

- 代码：测试命令、结果、限制、必要的 commit。
- 数据：源清单、审核规则、保留/剔除数量、转换后 episode/frame 数。
- 训练：数据集版本、采样配比、模型/base checkpoint、超参数、seed、checkpoint、loss 与验证结果。
- MuJoCo：场景版本、控制映射、rollout 成功率或失败模式。
- 真机：安全参数、初始姿态、测试任务、次数、成功/失败原因、是否有碰撞或异常动作。

## 8. 文档同步

当入口、数据格式、控制语义、训练配置或安全限制变化时，同步更新对应文档。长期规则写入 `AGENTS.md`；具体流程写入 `docs/`；一次性实验细节写入实验记录或训练输出，不要把所有细节塞进根规则。
